# Changelog

Platform releases use `vX.Y.Z` tags. This fork (goodloris/LoopForge) publishes `ghcr.io/goodloris/loopforge` from 0.5.0 on; 0.4.0 and earlier were published upstream as `ghcr.io/tencent/loopforge`. LoopForge Local packages use `local-vX.Y.Z` tags and are published by manually running the `release-local` workflow.

## Unreleased

- Feishu (飞书) web login, for the China edition at `open.feishu.cn`, offered as a 飞书登录 button beside password sign-in. A Feishu member signing in for the first time is auto-provisioned a new account and recognised afterwards only by their Feishu identity — (`union_id`, `tenant_key`), or (`open_id`, `tenant_key`) when the app has no union id — never by login name, Chinese name or email, so it cannot take over a password account. Enable it by setting `LOOPFORGE_FEISHU_APP_ID` and `LOOPFORGE_FEISHU_APP_SECRET`; the button stays hidden otherwise. `LOOPFORGE_FEISHU_ALLOWED_TENANTS` is a comma-separated `tenant_key` allowlist that **denies every sign-in when empty or unset** (auto-provisioning with no tenant limit would admit any Feishu user); a denied member sees their `tenant_key` on the error page and in the log so an admin can allowlist it. `LOOPFORGE_FEISHU_REDIRECT_URI` is optional and derived from the request when unset. Provisioning obeys `AGENTFLOW_ALLOW_SIGNUP` (when `false`, only already-bound members sign in), the first account becomes the administrator, and new accounts join the welcome project, matching password registration. The OAuth state is a random 32-byte value kept server-side for 10 minutes, mirrored in an HttpOnly `SameSite=Lax` cookie and consumed once, so a missing, mismatched, expired or replayed callback is rejected. Only the login scope is used (three `net/http` calls: `app_access_token/internal`, `authen/v1/oidc/access_token`, `authen/v1/user_info`); no contact/directory API is called, and the app secret, authorization code and tokens never appear in logs. The binding lives in a new `user_identities` table keyed by (`provider`, `tenant`, `subject`), shared by any future sign-in provider, so no columns are added to `users`. Startup AutoMigrate creates it; existing installs can also apply `migrations/039_user_identities.sql` (MySQL) or `migrations/postgres/039_user_identities.sql` (PostgreSQL) by hand. See `docs/deployment.md#feishu-飞书-login`. The legacy enterprise-SSO `/api/auth/exchange` still does not verify an OAuth state; that is unchanged and out of scope here.
- The product is renamed from Bagel to **LooPool**. Every user-visible "Bagel" in `web/` and `chatbot/` becomes "LooPool" (page titles, login, chat home wordmark, the cloud-runner label 「LooPool 云端」, OAuth/bot-bind pages, VS Code page, usage report, English i18n), the brand files are renamed `web/loopool-mark.svg`, `web/loopool-logo.svg`, `web/images/loopool-mark.png` and `chatbot/src/LooPoolMark.jsx`, and the wordmark reads LooPool. The leftover LoopForge logo is gone: the boot loader's blue-violet "b" curve is replaced by the ring mark, and the chat home title sweep uses the ring's crust colours instead of the old cyan/blue/violet palette. The ring artwork itself is kept until LooPool-specific artwork is provided. `web/brand_test.go` now rejects a readable "Bagel" as well as "LoopForge", and guards that the boot loader and chat home no longer carry the old logo. Seed labels say 「LooPool 体验项目」 and owner `LooPool`; existing installs run `044_loopool_builtin_labels.sql` by hand (MySQL: `migrations/044_loopool_builtin_labels.sql`, PostgreSQL: `migrations/postgres/044_loopool_builtin_labels.sql`), which renames a welcome project still called 「LoopForge 体验项目」 or 「Bagel 体验项目」 and an owner still `LoopForge` or `Bagel`, so 042 need not run first. Idempotent; `scripts/manual-migration-hints.sh` reports it while pending. Internal identifiers and backend strings that say LoopForge are unchanged.

## 0.7.0 — Bagel branding and a configurable default executor

**Upgrading an existing installation**: run `git checkout v0.7.0 && ./start.sh pull`, then run these two migrations by hand, in order. Both are idempotent (safe to run again; a second run changes nothing), and the installer and `./start.sh pull` print the command while either is pending (`scripts/manual-migration-hints.sh`). 039 and 040 are reserved for the next release.

- `041_builtin_roles_default_executor.sql`: built-in SOP roles and 基线对齐执行员 drop `executorId: codebuddy` and follow the default executor. Only the value `codebuddy` is removed; a role switched to another CLI keeps it. Idempotent.
  - MySQL: `docker compose exec -T mysql sh -c 'MYSQL_PWD="$MYSQL_PASSWORD" mysql -u loopforge loopforge' < migrations/041_builtin_roles_default_executor.sql`
  - PostgreSQL: `docker compose exec -T postgres psql -X -v ON_ERROR_STOP=1 -U loopforge -d loopforge < migrations/postgres/041_builtin_roles_default_executor.sql`
- `042_bagel_builtin_labels.sql`: the welcome project 「LoopForge 体验项目」 becomes 「Bagel 体验项目」 and the built-in SOP cards' author tag `LoopForge` becomes `Bagel`. Only values still at the shipped original change; a renamed project or edited owner is left alone. Idempotent.
  - MySQL: `docker compose exec -T mysql sh -c 'MYSQL_PWD="$MYSQL_PASSWORD" mysql -u loopforge loopforge' < migrations/042_bagel_builtin_labels.sql`
  - PostgreSQL: `docker compose exec -T postgres psql -X -v ON_ERROR_STOP=1 -U loopforge -d loopforge < migrations/postgres/042_bagel_builtin_labels.sql`

New environment variable `AGENTFLOW_DEFAULT_EXECUTOR`: unset means CodeBuddy and nothing changes; set it to `kiro` (for example) and the UI hides CodeBuddy-only setup and built-in roles run on the default executor. **Behaviour changes to expect**: a chat turn, including a steer (插话/立即发送), whose selected CLI is unavailable is refused with what to configure for that CLI instead of falling back to CodeBuddy. **Known limitations**: the preview-build node still always runs on CodeBuddy; #37's marking of unavailable CLIs in the picker and the `start.sh` hint are not done; Feishu sign-in and GitLab (#40, #41) are not in this release and come next.

### 行为变化

- An unavailable CLI is refused instead of replaced by CodeBuddy (#38). A chat turn (`POST /api/assistant/generations`, `POST /api/assistant/chat`) that picks a non-CodeBuddy CLI without its credentials or login fails with that CLI's message (`assistantEngineMissingKey`), and the conversation is no longer saved as CodeBuddy. Steer (插话/立即发送) checks the turn's own CLI instead of requiring a CodeBuddy key, refuses an unavailable CLI and a CLI switch like a new turn, and keeps a Kiro conversation on Kiro. When `AGENTFLOW_KIRO_DATA_DIR` is set but holds no login, the Kiro refusal adds 「Compose 部署请在 .env 设置 LOOPFORGE_KIRO_DATA_DIR 并 docker compose up -d」, and the platform warns at startup. `docs/deployment.md` says to recreate the container after editing `.env`.

### 默认执行器

- The default executor is configurable with `AGENTFLOW_DEFAULT_EXECUTOR` (#43). It must be a supported executor ID; an invalid value falls back to `codebuddy` with a single warning, and unset keeps CodeBuddy. `/api/assistant/models` returns `defaultExecutor` and the chat and console use it instead of a hard-coded `codebuddy`, only for new conversations (an existing conversation keeps its executor). Missing-credential messages name the executor actually requested. Conversation titles are generated with the conversation's own executor and model when the user has no CodeBuddy key. Documented in `docs/deployment.md`, `.env.example` and `compose.yaml`. Approval review, AI notification summaries, Bot replies, clarification defaults and run evals are unchanged.
- Built-in roles follow the default executor (#44). The roles of the four built-in SOPs and 基线对齐执行员 no longer store `executorId: codebuddy`; a role or node without an executor resolves to `AGENTFLOW_DEFAULT_EXECUTOR` (CodeBuddy when unset) both when it runs and in the UI's dependency checks. New installs get this from the seed; existing installs run `041_builtin_roles_default_executor.sql` by hand (MySQL and PostgreSQL). `/api/bootstrap` reports `defaultExecutor`.

### 界面

- The console and chat UI are rebranded to **Bagel** (#39): a new ring mark and wordmark (`web/bagel-mark.svg`, `web/bagel-logo.svg`) drive the favicon, apple-touch-icon, login logo and the chat home logo, and every user-visible "LoopForge" in the `web/` and `chatbot/` frontends becomes "Bagel" — page titles, the chat home wordmark, the cloud-runner label 「Bagel 云端」, the usage report, the role editor's platform-MCP switch, and the English i18n dictionary. Internal identifiers (`LoopForgeGitSSH*`, `loopforge.*` storage keys, `LOOPFORGE_*` env, the ghcr image, `.loopforge/verify`), links to the upstream repository, and backend strings are left unchanged. `web/brand_test.go` now guards that no readable "LoopForge" remains in the frontend (the way it used to guard "AgentFlow"). The Bagel artwork comes from agenzo-rsi `apps/console-ui` and is reused with permission; see design.md「设计参考」.
- The two remaining 「LoopForge」 labels are gone: the welcome project is 「Bagel 体验项目」 and the built-in SOP cards' author tag (`Workflow.owner`) is 「Bagel」. New installs get them from the seed; existing installs run `042_bagel_builtin_labels.sql` by hand (MySQL and PostgreSQL), which renames only a welcome project still called 「LoopForge 体验项目」 and changes only an owner still `LoopForge`. `web/brand_test.go` now also checks the seed. The project key `LOOP` is unchanged.
- With a default executor other than CodeBuddy, CodeBuddy-only setup is hidden (#44): the platform-admin 共享 CodeBuddy Key tab and per-account key badges, the CodeBuddy key block of the quick-access wizard (whose first step then needs no model key), and the CodeBuddy recommendation in personal settings 下一步, which names the default CLI's credential instead. SOP cards and the 使用「…」 dialog compute dependencies from each role's real executor (Kiro shows 「Kiro CLI 本机登录 ✓」). The login page no longer links to the upstream GitHub repository. With CodeBuddy as the default the UI is unchanged.

## 0.6.0 — Kiro CLI across conversation workspaces, and the v0.5.0 acceptance fixes

**Upgrading an existing installation**: run `git checkout v0.6.0 && ./start.sh pull`. An existing installation runs `migrations/038_generic_sop_gates.sql` (MySQL) or `migrations/postgres/038_generic_sop_gates.sql` (PostgreSQL) by hand; the installer and `./start.sh pull` print the command while it is pending (`scripts/manual-migration-hints.sh`). There is no other data migration: the new `mr_delivery_states.landed_at` column is added by startup AutoMigrate. On macOS set `LOOPFORGE_KIRO_DATA_DIR` to an absolute path, quoted when it contains spaces: `LOOPFORGE_KIRO_DATA_DIR="/Users/<you>/Library/Application Support/kiro-cli"`. A source build in mainland China can set `GOPROXY` and `NPM_CONFIG_REGISTRY` to local mirrors. **Behaviour changes to expect**: a new or re-enabled schedule job runs at its next scheduled time, not on the next tick, and an interval job one interval later; a failed run releases its admission slot; and an SOP trigger with no source set in 「同步哪些来源」 dispatches without pulling. **Known limitations**: requirements that were already duplicated are not renumbered; Bot replies and AI notification summaries have not been tested on the WeCom (企业微信) channel; Kiro in a Docker sandbox reaches platform tools through the stdio bridge, which waits up to 10 minutes for a single tool call; and #33's `@builtin` trust is retained.

### 行为变化

- A failed script node or command gate keeps its command, exit code and the tail of its output (80 lines, 4000 bytes) in the node output and error, and hands them to the node it reworks or retries. Before, the reworked node only saw `Run: exit status 1`. The output no longer goes into the error value the engine classifies, so a test log that prints `signal: killed` or `max turns` no longer changes how the failure is handled.
- The built-in backend, frontend and defect-fix SOPs: 独立评审 and 测试验证 rework 开发实现 (`maxReworks` 2) instead of rerunning the review and failing the run, and 测试验证 gates on the exit code of `.loopforge/verify` from each repository's target branch. Without that file the test verdict stays the Agent's and `test-report.md` says so. New installs get this from the seed; existing MySQL and PostgreSQL installs run `migrations/038_generic_sop_gates.sql` or `migrations/postgres/038_generic_sop_gates.sql` by hand, and `scripts/manual-migration-hints.sh` names it while it is pending.

### Kiro

- Kiro CLI reaches the platform session MCP server in a Docker conversation sandbox (D3, the real cause). The earlier `--trust-tools` change (below) was not enough: in the acceptance environment, whose `kiro-cli` login is an enterprise IAM Identity Center profile, workspace chat still reported `agentflow__*`, `workbench_tool_schema` and `submit_assistant_reply` unavailable and made no gateway request. Reproduced in a container against both `kiro-cli` 3.4.0 and 3.5.0: under this enterprise profile (`mcpSandboxing`/`sandboxNetworkMode` locked) `kiro-cli` only connects an HTTP MCP server on a **loopback** address — it counts a non-loopback server (`session.load.timing mcpServers:1`) but never dials it (`mcp.log` has only `[MCPConfigManager] Identity provider setting changed`). A Docker conversation's session relay is advertised at the platform container's non-loopback IP (`conversationDockerAccess`), so Kiro silently dropped it; platform-mode chat and requirement clarification worked only because their gateway is same-container loopback, and SOP nodes because their servers are loopback (the agent browser) or stdio (the gate server). Trust was never the differentiator — both `--trust-all-tools` and `--trust-tools=@builtin,@agentflow_session` connect on loopback and both fail on a non-loopback URL. The fix: for a Docker sandbox, the Kiro session gateway is now exposed as a **stdio** command MCP server (a `python3` bridge that pipes JSON-RPC to the relay URL) instead of an HTTP url. A stdio child is not subject to Kiro's MCP network sandboxing, so it reaches the relay, the same way the SOP gate server already does; `python3` is already required for the native approval hook. It applies in platform, workspace and resume conversations (all go through the one conversation-process start path), only for Kiro and only for a Docker sandbox, and touches neither the loopback agent browser, the `#28` clarification `permissions.yaml`, nor the D1 approval hook. Verified in a container end-to-end: `kiro-cli` 3.4.0, fed the exact `mcp.json` the fix emits, connects over stdio to a cross-container relay and the model calls a platform tool. Upgrading the pinned `kiro-cli` to 3.5.0 does **not** fix D3 and is not done.
- Kiro CLI trusts `@builtin` plus the session MCP in a workspace conversation. A conversation left in workspace mode launched `kiro-cli` with bare `--trust-all-tools`; headless Kiro only connects an MCP server it can name in `--trust-tools`, so it now runs `--trust-tools=@builtin,@<each MCP server>`: `@builtin` trusts every built-in tool (so `web_fetch`, `web_search` and any tool a future Kiro adds keep working, with no list to maintain), and naming each MCP server matches the form platform-mode chat and requirement clarification already use. This does not widen Kiro's write trust: platform writes proposed from a workspace phase still wait as drafts for a person (gateway catalog and draft flow), and SOP nodes keep `--trust-all-tools`. (This is the workspace trusting every built-in tool and naming the session MCP; it is necessary for built-in tools in workspace mode but, as the entry above records, was not what made the session MCP reachable — the D3 fix is #36, the entry above.)
- Requirement clarification (「帮我问清楚」) runs on the CLI picked in the clarification panel, Kiro CLI included. It still runs on the platform server in the checked-out repository: Kiro CLI uses the server's `kiro-cli` login (in Compose the login copy from `LOOPFORGE_KIRO_DATA_DIR`) and trusts only its read-only file tools (`read`, `grep`, `glob`) and the platform MCP server that takes `submit_clarification`; answer rounds resume the same Kiro session. File reads of both Kiro CLI and CodeBuddy clarifications are confined to the checkout (the requirement text can come from anyone who files an issue, and the rest of the server holds its secrets): Kiro CLI through a `fs_read` deny rule outside the checkout in its private `permissions.yaml`, CodeBuddy through a PreToolUse hook that refuses file-tool paths resolving outside it. Before, both could read any file the platform process could, e.g. `/proc/1/environ`. With no model chosen, a responsible user without a CodeBuddy key gets `kiro:auto` when the server can run it. The CodeBuddy-only refusal is gone: a missing `kiro-cli` or login, or a missing personal key of the chosen CLI, is refused before any checkout with what to configure. CodeBuddy clarifications are unchanged.

### 调度

- A new schedule job no longer runs on the next scheduler tick (D30). A Cron job first runs at the first Cron time after it is created, an interval job one interval after. Re-enabling a job, or changing its `cron` or `intervalSec`, restarts the count from that moment instead of running the occurrences missed meanwhile; the moment is kept in the server-managed `scheduleFrom` (stored in the job payload, no migration). Jobs saved before the upgrade that never ran count from service startup, so the upgrade does not fire them all at once. 「立即运行」 still runs at once.
- SOP trigger jobs with 「同步哪些来源」 set to GitHub, 工蜂 or TAPD pull that source into the project before dispatching, so one Cron both pulls and dispatches; 「所有已配置来源」 still only dispatches issues already imported. Imported GitHub and Gongfeng issues take the next project number and keep the external number as `externalRef.externalIid` (shown as 「GitHub #N」). A trigger job that prefers the issue's SOP ignores the project default filled in on save (`workflowDefaulted`). Only running SOPs hold a project or machine slot: runs waiting on a human gate, failed or cancelled give it back, and approving, resuming or retrying them queues when the bucket is full. Idle containers of runs waiting on a human gate are reclaimed after 10 minutes instead of 2 hours (#27). **Existing data is not migrated**: issues imported earlier keep their duplicate numbers, and they have no `workflowDefaulted`, so a trigger job that prefers the issue's SOP still runs the default bound to them.

### 交付统计

- Delivery state now waits for the default branch (#21). An SOP that succeeds with its MR still open, or merged only into the integration branch, leaves the requirement at `deliveryState=pending`, status `in_review` (shown as 「MR 待合入」 / 「已合入集成分支」), instead of locking it as `merged`/`done`. The MR sync marks it delivered once every MR is on the default branch, including GitHub pulls whose integration branch was promoted. A pending requirement can be triggered again. **Requirements already locked before this change are not corrected**: one that shows 「交付闭环」 or `done` while its MR is still open or only on the integration branch stays that way, and MR polling does not revisit it. There is no data migration.
- Analytics `mergedMrs` (overview summary and trend, business-domain `deliveryMetrics` and `deliveryTrend`) counts only MRs merged into the repository default branch. Merges into the integration branch move to the new `integratedMrs`; merged MRs whose target branch is not recorded yet are left out until the MR sync fills it in. A work MR merged into the integration branch counts as merged once the integration branch is promoted, dated by the promote MR's `merged_at` (a new `mr_delivery_states.landed_at` column, added by startup AutoMigrate), and leaves `integratedMrs`. A promotion without a promote MR (direct push to the default branch) has no reliable time, so such an MR stays in `integratedMrs`. GitHub promote PRs are now recorded like Gongfeng promote MRs. Already-promoted MRs are dated on the first MR sync after the upgrade when their promote MR is on record (GitHub lists up to 100 promote PRs; Gongfeng keeps the promote MRs it has discovered so far). Completion-to-merge latency uses default-branch merges only. Earlier reports counted integration-branch merges as merged MRs.

### 界面

- UI fixes from the v0.5.0 acceptance run: 「待我确认」 lists every human gate of the user's projects, grouped into 「指派给我」 and 「项目内其他」, with viewers read-only; the badge counts only gates the user can act on (D5). The project wizard and members tab choose 成员 / 维护者 / 查看者; saving project settings used to reset every member to `member` (D8). Escape in a member picker closes only the picker (D9). Project SOP cards can be copied from 「⋯」 (D17). Toasts close at most 10 s after their normal time even under the pointer and sit at the top centre, clear of heading actions (D18). The task IDE is no longer reloaded when the run re-renders (D19). Project pages count requirements without opening the list first, and the SOP page headline says how many runs the listed SOPs account for (D20). The SOP trigger card is laid out on separate lines (D24). The trigger config reloads SOPs, so ones created since page load appear in 「默认 SOP」 (D25). SOPs gated on `.loopforge/verify` say in the designer and in a requirement's 执行进展 tab when the target branch has no such file (new read-only `GET /api/workflows/{id}/verify-gate`, see `docs/deployment.md#test-command-gate`).

### 安装和部署

- `scripts/install.sh` and `scripts/dev.sh` (so `./start.sh`, `./start.sh dev`, `pull` and `restart`) read `.env` with a parser instead of `source`-ing it as a bash script (D31). An unquoted value with spaces, such as `LOOPFORGE_KIRO_DATA_DIR=/Users/x/Library/Application Support/kiro-cli`, which Compose accepts, used to abort them with `Support/kiro-cli: No such file or directory`. Comment lines, an `export ` prefix and matching single or double quotes are handled as Compose does; `$(...)`, `$VAR` and `~` are taken literally and never run. `${VAR}` interpolation inside `.env`, which Compose supports and the generated `.env` does not use, is not expanded by the scripts. The docs now ask for an absolute `LOOPFORGE_KIRO_DATA_DIR`, quoted on macOS: `LOOPFORGE_KIRO_DATA_DIR="/Users/<you>/Library/Application Support/kiro-cli"`.
- A chat workspace bound to a host that is gone is taken over by the instance serving the conversation instead of failing every message (D33). Rebuilding the platform from source (`./start.sh dev`) gives the container a new hostname, so a saved conversation that still named the old one used to fail with `工作区控制通道配置错误：…请为 API 和 Worker 配置相同的 AGENTFLOW_CONTROL_TOKEN`, even though single-container deployments correctly have no control token. The checkpoint archive lives in the database, so when no live worker still advertises the bound host (`EngineInstancesRepo.WorkspaceHostAlive`) and the run is not on an execution machine, the instance rebinds the workspace to itself under the lease it already holds and restores from the saved checkpoint; an unsaved workspace is taken over in place only when its checkout is still on local disk (the data volume persisted across the rebuild). A workspace a live worker or instance still advertises, and one on an execution machine, are never reclaimed, so real multi-instance and split-worker owners keep theirs. **No data migration**: pre-upgrade rows that still name a retired hostname are handled by this runtime check on first use. The control-channel error now reports an offline or unreachable owner first and only mentions `AGENTFLOW_CONTROL_TOKEN` when the workspace genuinely lives on another reachable instance.
- The first message after a platform-host rebuild no longer fails on the reclaimed chat workspace (D33 follow-up). The takeover above runs under the turn's workspace lease, but the native CLI start resolved the workspace from the run snapshot captured *before* the takeover, so the first message failed with `工作区暂不可用：工作区绑定在其他 LoopForge 实例` while only the second — dispatched with an already-rebound snapshot — succeeded. The start path now resolves the local workspace from the committed bind after the lease reclaims it. The takeover decision is unchanged, so a workspace a live worker or instance still advertises is never stolen; only the stale in-memory judgment is corrected.

## 0.5.0 — PostgreSQL by default, published from this fork

- `compose.yaml` pins `ghcr.io/goodloris/loopforge:0.5.0`, published by this fork's `release` workflow, for the platform and for `AGENTFLOW_ISOLATED_IMAGE`. Earlier pins pointed at `ghcr.io/tencent/loopforge`. 0.5.0 is based on upstream 0.4.0 (synced below) plus this fork's PostgreSQL support; `ghcr.io/tencent/loopforge:0.4.0` itself runs on MySQL only. `MIRROR=<host>` now pulls `<host>/goodloris/loopforge:<version>`.
- A new `./start.sh` installation of the published image uses PostgreSQL. The pinned image supports it, so the installer no longer probes the image for `-database-dsn` and no longer switches a new installation to MySQL.
- MySQL stays supported: `LOOPFORGE_DATABASE=mysql ./start.sh` on the first run. New `.env` keys: `LOOPFORGE_DATABASE` (`postgres` or `mysql`), `LOOPFORGE_COMPOSE_DSN` (in-network DSN), `COMPOSE_PROFILES`, and `LOOPFORGE_POSTGRES_PORT` for the host port of the PostgreSQL service. The platform reads `AGENTFLOW_DATABASE_DSN` (flag `-database-dsn`); `AGENTFLOW_MYSQL_DSN` remains an alias.
- **Upgrading an existing installation**: check out `v0.5.0` and run `./start.sh pull`. A `.env` without `LOOPFORGE_DATABASE` was created on MySQL; it gets `LOOPFORGE_DATABASE=mysql` and keeps its data. There is no MySQL-to-PostgreSQL migration. A `LOOPFORGE_IMAGE` saved in `.env` still wins over the new pin; remove it or set it to `ghcr.io/goodloris/loopforge:0.5.0`. Apply the manual migrations listed below (031, 033, 036, 037) as before; fork migrations 034/035 were renumbered to 036/037.

- Synced with upstream Tencent/LoopForge `v0.4.0` (merge, not rebase). The upstream changes are listed under 0.4.0 below. On PostgreSQL, the new schedule execution history and the attachment cleanup search payload text with `strpos(payload::text, …)` instead of `INSTR(CAST(payload AS TEXT), …)`, which PostgreSQL does not have; the two new tables and the `user_configs.codebuddy_models` column are created by startup AutoMigrate on both databases.
- Fork migrations renumbered to make room for upstream 034 and 035: `034_generic_backend_pip.sql` is now `036_generic_backend_pip.sql` and `035_generic_test_role_requires_tests.sql` is now `037_generic_test_role_requires_tests.sql`. Only the file names (and the file names quoted in their header comments) changed; the SQL is the same and idempotent. A database that already ran the old 034/035 needs nothing: rerunning 036/037 changes no row. Upstream `034_schedule_job_executions.sql` and `035_codebuddy_model_catalog.sql` are optional DDL that startup AutoMigrate also applies; neither is needed on PostgreSQL (see `migrations/postgres/README.md`).
- New installations use PostgreSQL. `./start.sh`, `scripts/install.sh` and `scripts/dev.sh` start a `postgres:17` service initialized as UTF8 with `C.UTF-8` collation and ctype, point the platform at it with `AGENTFLOW_DATABASE_DSN`, and after the platform is healthy apply `migrations/postgres/001_baseline_extensions.sql` and `migrations/postgres/seed/*.sql`. MySQL stays supported: choose it on the first run with `LOOPFORGE_DATABASE=mysql ./start.sh`. `compose.yaml` puts the two database services under the Compose profiles `postgres` and `mysql`, and `.env` records the choice as `LOOPFORGE_DATABASE` with the in-network DSN `LOOPFORGE_COMPOSE_DSN`. **Existing installations keep MySQL**: the first `./start.sh`, `./start.sh pull` or installer run after updating adds `LOOPFORGE_DATABASE=mysql` to a `.env` that lacks it and says so; secrets and data are unchanged. Its command gate checks every writable repository of the run: one with commits beyond the target branch fails while it has uncommitted changes, while its checkout is off the run's work branch, or until `git ls-remote origin` shows that work branch at HEAD. A second gate of the new mode `mr` has the engine look the MR up on the host with the same lookup delivery tracking uses (GitHub and Gongfeng): every writable repository whose work branch on origin carries commits beyond the target branch needs an MR from that work branch into that target branch that carries the pushed tip: an open one whose head is the tip (or whose host reports no head), or a merged one whose head is the tip. An agent that reports pass without opening an MR, opens it against the wrong branch, or leaves only an earlier merged MR on a reused work branch does not reach 交付汇总. The lookup runs as the run: on GitHub with the Git token the run pushed with (its responsible user's), falling back to the Owner of the run's own project; on Gongfeng through the run project's MCP as the responsible user. Run-scoped commands now get `AGENTFLOW_WORK_BRANCHES` (one `dir<TAB>work branch<TAB>target branch` line per writable repository) and repository-scoped commands get `AGENTFLOW_WORK_BRANCH` and `AGENTFLOW_BASE_BRANCH`; the target branch is the one frozen into the run, including a requirement's release branch and a scheduled SOP's integration branch. 交付汇总 no longer pushes or opens a PR itself. SOPs already adopted into a project are copies and keep their old graph. The product SOP delivers documents only and is unchanged.
- A conversation reply that is still running keeps running through a slow heartbeat. A poll, the conversation list, a follow-up message or a steer used to record it as interrupted after 45 seconds without a stored heartbeat; the process then cancelled the CLI and the next message failed with 「工作区正在使用或保存，请稍后重试」 for up to 15 minutes. Reads of a turn this process executes no longer reap it, and an unchanged heartbeat on MySQL no longer counts as a lost turn. - `loopforge install <host>` defaults to Classic; Portable uses the distinct `loopforge skills install <host>` command group.
- Added explicit `--force` to overwrite installation; by default it still stops on user file or symlink conflicts.
- `install --force` supports switching between Classic and Portable editions on the same host.
- CodeBuddy Portable stage executors and research assistants uniformly enable auto-run and `bypassPermissions`.
