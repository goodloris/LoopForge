# Changelog

Platform releases use `vX.Y.Z` tags. This fork (goodloris/LoopForge) publishes `ghcr.io/goodloris/loopforge` from 0.5.0 on; 0.4.0 and earlier were published upstream as `ghcr.io/tencent/loopforge`. LoopForge Local packages use `local-vX.Y.Z` tags and are published by manually running the `release-local` workflow.

## Unreleased

### Changes

- 角色向导的 Codex / Claude Code 模型下拉只列出当前用户可用的模型。`GET /api/executor-models` 的 `codex`、`claude` 新增 `availability`（`verified` / `unverified` / `none`）和 `notice`，`source` 必定有值：用户保存了模型目录或 Base URL 探测成功时只列这些模型（`verified`）；只有官方端点 Key，或有一台报告了该 CLI 且使用账号登录的执行机器时，列出内置清单并逐项标「（未验证）」，不预选模型（`unverified`）；两者都没有（含未登录）时返回空列表和配置引导（`none`），仍可手动输入模型 ID。这是行为变化：以前无凭据用户也会拿到完整内置清单。`?builtin=1` 和其他 CLI 不变。
- 保存角色（`PUT /api/agents`、通用模板 `PUT /api/workflows/:id/agents`）时校验 Codex / Claude Code 模型：保存人有已验证清单而模型不在其中时返回 400，除非请求体带 `customModel: true`（手动输入，不入库）；无法验证时照常保存。两种情况都会在响应里多一个 `warnings` 数组，向导会弹出提示。已有角色的执行器和模型不变时不再校验，存量 SOP 不受影响。新填写的模型 ID 还要满足字符规则（非空、不超过 128 个字符、不以 `-` 开头、不含空白/引号/反斜杠）。校验只针对保存人自己的凭据；运行时用的是 SOP 责任人的凭据，「已验证」也不保证额度或网关一定放行。
- No data migration and no SQL to run.

## 0.9.0 — Self-hosted GitLab delivery, Kiro credits and Loopool

**Upgrading an existing installation (from 0.8.0)**:
1. `git checkout v0.9.0 && ./start.sh pull`. No schema change blocks startup; startup AutoMigrate adds no new table this release, and nothing has to run before the platform starts.
2. After startup, run `045_loopool_lowercase_builtin_labels.sql` (repeatable): it lowercases the capital P in the built-in display labels 044 wrote, so the welcome project reads 「Loopool 体验项目」 and the four built-in SOP templates' owner reads `Loopool`. It changes only values still at the `LooPool` capitalisation; a renamed project or edited owner is left alone, and 044 need not run first. Purely cosmetic — the labels a user reads — so it is safe to run any time after the upgrade, not before. New installs get the Loopool labels from the seed.
   - MySQL: `docker compose exec -T mysql sh -c 'MYSQL_PWD="$MYSQL_PASSWORD" mysql -u loopforge loopforge' < migrations/045_loopool_lowercase_builtin_labels.sql`
   - PostgreSQL: `docker compose exec -T postgres psql -X -v ON_ERROR_STOP=1 -U loopforge -d loopforge < migrations/postgres/045_loopool_lowercase_builtin_labels.sql`

`045_loopool_lowercase_builtin_labels.sql` is the only migration added since 0.8.0 (the earlier manual migrations 036/037/041/042/044 are unchanged; an installation already on 0.8.0 has run the ones it needed). `./start.sh pull` and `scripts/manual-migration-hints.sh` print 045 while it is still pending.

New optional environment variable `AGENTFLOW_ALLOW_PASSWORD_SIGNUP` (see below) closes only password self sign-up; unset it keeps the previous behaviour. Using a self-hosted GitLab needs no migration: an administrator authorizes the host under 平台管理 → Git HTTPS 主机授权 (platform type GitLab), and each user adds a GitLab access token with the `api` scope for that host in 个人配置.

### Changes

- New `AGENTFLOW_ALLOW_PASSWORD_SIGNUP` closes only password self sign-up. Unset or empty inherits `AGENTFLOW_ALLOW_SIGNUP` (existing deployments behave as before); `false`/`0`/`no`/`off` makes `POST /api/auth/register` answer 403 and hides the login page's 注册 entry, while Feishu auto-provisioning still follows only `AGENTFLOW_ALLOW_SIGNUP` and the tenant allowlist. It cannot reopen sign-up when `AGENTFLOW_ALLOW_SIGNUP=false`. When Feishu sign-in can still create the account, the 403 reads 「自助注册已关闭，请使用飞书登录，或联系管理员创建账号」. `/api/auth/setup` and `/api/platform/accounts` add `passwordSignupEnabled`; `signupEnabled` keeps its meaning (any self-service path). 平台管理 → 成员账号 says when only password sign-up is closed. `compose.yaml` passes the variable through (empty by default).
- The first-account rule counts every user, as Feishu provisioning already did: `needsSetup` and the administrator granted to the first password registration now require no user at all, instead of no password account. On a Feishu-only deployment (users but no password account) the login page no longer asks for setup and a password registration no longer becomes administrator. A fresh empty install is unchanged. If a new install got a user through another sign-in method before its administrator, create the administrator with `loopforge-account -admin`.
- A registration refused because sign-up is closed no longer spends the per-IP password attempt budget.
- No data migration and no SQL to run.
- GitLab 端到端验收修复（接 #58）：
  - **控制面 HTTPS push 凭据丢失（根因在共享 helper）**：`internal/gitwork/http_credentials.go` 的 `httpCredentialForCommand` 在扫描命令参数找「内联远端 URL」时，把 push/fetch 的 refspec 也当成了远端。`HEAD:refs/heads/<branch>` 是 scp 歧义串（`scpHost` 把第一个冒号前、无斜杠的 `HEAD` 读成主机名），于是 `IsSSHReference("HEAD:refs/heads/x")` 为真，覆盖了上下文里真正的 HTTPS 远端（`WithHTTPRemote`），再 `url.Parse` 得到非 https scheme → 返回空凭据 → git 回落交互式提示 → `fatal: could not read Username ... terminal prompts disabled`。fetch 的 refspec（`+refs/heads/a:refs/remotes/origin/a`，冒号前有斜杠）不被误判，所以同一次对齐里 fetch/merge 成功、只有 push 失败。修复：参数扫描只认显式 `http(s)://` URL 覆盖上下文远端，不再把 SSH 引用（含 refspec）当远端——HTTPS 凭据本就只对 http(s) 远端有意义。这是**共享函数一次性修复**，覆盖所有走该 helper 的控制面 push：基线对齐（`engine/align.go`、`runner/align.go`）、集成合入/promote（`engine/integrate.go`、`runner/integrate.go`）、工作分支交付（`gitwork/workbranch.go` 的 `HEAD:refs/heads/<branch>`）。GitHub 走同一条 helper、同样用该 refspec 形式，之前存在相同潜在缺陷，此修复同时覆盖 GitHub。回归测试 `TestBareRemoteRefspecResolvesContextCredential`（撤销 fix 即红、恢复即绿）。
  - **平台兜底开出空 MR**：`tracker/gitlab.go` 的 `EnsureBranchMR` 在创建前先确认源分支在远端存在（`GET /repository/branches/:branch`）且相对目标分支有提交（`GET /repository/compare?from=target&to=source` 的 commits 非空）；任一不满足则不创建，返回 `domain.BranchNotDeliverableError`（非失败）。`engine/lifecycle.go` 的 `deliveryMRsFromRun` 捕获它并写一条可读运行事件 `mr.delivery_skipped`（说明工作分支未推送或无改动），不再在工作分支未落地时开出无 head_sha、0 改动、源分支 404 的空 MR。GitLab 本身允许用不存在/无提交的源分支建 MR，故需平台侧前置校验。测试覆盖「分支缺失」「无新提交」两种跳过与正常创建路径。
  - **集成路径开出 0 提交 MR**：定时运行即使没有任何改动也照常推送工作分支，随后集成路径（`engine/integrate.go` → `MergeIntoBranch` → `tracker/gitlab.go` 的 `EnsureAndMergeBranchMR`/`gitlabMergeBranch`）会开出一个 0 提交的 work→int MR 再 `auto_merge_failed`。把上条的「远端分支存在 + compare 有提交」检查抽成 `gitlabClient.requireDeliverableBranch` 一个函数，`EnsureBranchMR` 与 `gitlabMergeBranch` 创建 MR 前都调用它（不写第二份）；没有提交时返回 `domain.BranchNotDeliverableError`。`integrate.go` 把它记成可读事件 `integration.skipped`（「工作分支相对 int 没有新提交，未开集成 MR」），不算失败、也不直推基线。测试覆盖 tracker 侧跳过不 POST 与 engine 侧记事件不直推。GitHub 对 0 提交的 PR create 返回 422「No commits between」→ 当前按 `auto_merge_failed` 计为失败（本次不改 GitHub）。

- 自托管 GitLab 实例的 SOP 端交付补齐。上游已经提供每主机 HTTPS Git 凭据（`domain.GitHTTPCredential`，GitLab 用 `PRIVATE-TOKEN`，API 基址 `https://<host>/api/v4`）、管理员 HTTPS 主机授权 + `gitegress` 出网校验、MR 项目键 `gitlab:<host>/<path>`、对话工作区 MR 发现与交付状态轮询（`refreshExternalDelivery`）。本次只补 SOP 侧缺口，复用这些模型，不新增平行实现：
  - 添加仓库：粘贴一个被管理员授权为 GitLab 的 HTTPS 主机上的仓库链接（支持子组、`/-/` 子页、`.git`、`git@`、`ssh://`，主机不符一律拒绝），登记为 `provider=gitlab`、`GongfengProjectID=gitlab:<host>/<path>`、HTTPS `cloneUrl`。主机是否 GitLab 由「平台管理 → Git HTTPS 主机授权」表达，因此不需要部署级 GitLab URL。未授权主机仍走通用 HTTPS Git 传输。新建项目向导、项目仓库表单与对话工作区向导在存在已授权 GitLab 主机时，标签/占位符/提示同时提到 GitLab，并把粘贴链接识别为「GitLab · host/path」，提醒配置该主机的 GitLab 访问令牌；`bootstrap` 新增 `gitHttpsHosts`（只含 host+platform，不含地址）。
  - SOP 交付：`EnsureAndMergeBranchMR`、`FindBranchMR`、`FindBranchMRsInto` 新增 `gitlab:` 分派，基于项目 Owner（或本轮责任人）该主机的 Git 访问令牌、经 `gitegress` 调用 GitLab v4 REST，查找/创建/合并 MR（merge commit，对 `405/406/409/422` 可合并性竞态按 GitHub 相同退避重试）。这让集成合入、`mode=mr` 校验门、权威交付 MR 解析对 GitLab 仓库生效；`.loopforge/verify` 分支文件检查本就是纯 git，无需改动。
  - 「发起 MR」节点与对话工作区提示词上游已是 provider 中立（`gh`、`glab`、`git credential fill`）。但平台镜像里并没有 `gh`/`glab` 二进制（Dockerfile 的 apt/npm 安装列表都没有），`command_binding.go` 写的 `glab` 只是找不到真实二进制就退出 127 的包装器，所以能否开 MR 取决于 agent 会不会自己调 REST API。为此补了平台兜底：SOP 交付解析（`engine.deliveryMRsFromRun`）在按工作分支找不到 MR 时，用负责人（回退项目 Owner）该主机的凭据经 `tracker/gitlab.go` 的 create 开一个（目标为基线分支）再解析（`Engine.EnsureBranchMR`→`Service.EnsureBranchMR`）。找不到时创建、已有时不重复创建、没有凭据时明确报错。GitHub/工蜂行为不变（兜底对它们是 pass-through，不自动创建）。
  - promote 落地检测（#24/D16/D29 口径）：新增 `syncGitLabWorkCommitsOnDefaultBranch` + `recordGitLabPromoteMRs` + `gitlabClient.mrOnBranch`，与 GitHub 的 `syncGitHubWorkCommitsOnDefaultBranch` 对齐——集成分支被提升（promote MR 合入默认分支、work 提交进入默认分支）后，work MR 由 integrated 变 merged，`landed_at` = promote 时间，`mergedMrs` 增、`integratedMrs` 减。`ApplyDefaultBranchLanding` 原先用只认 github.com/工蜂 的 `ParseGongfengMR` 解析 MR 链接，对 `gitlab:` 链接失效导致 `landed_at` 写不进去；改用覆盖 gitlab/ghe 的 `ParseDeliveryMRURL`（严格超集，GitHub/工蜂行为不变）。SOP 交付的 gitlab MR 没有登记人，`refreshExternalDelivery` 无法轮询，新增 `refreshGitLabDelivery` 用项目 Owner 凭据兜底刷新（对齐 GitHub 的 `refreshGitHubDelivery`）。
  - CI 门禁项目（`only_allow_merge_if_pipeline_succeeds=true`）：合并前先读 MR 的 `detailed_merge_status`（17.x）与 head pipeline。流水线运行中（`ci_still_running`/`ci_must_pass` 且 pipeline 为 running/pending 等）时，`PUT /merge` 带 `merge_when_pipeline_succeeds=true`（17.9 支持；`auto_merge` 参数 17.11 才加，故按 17.9 用 `merge_when_pipeline_succeeds`）排队自动合并，返回 `domain.MergeQueuedError`（既非失败也非已合并）；流水线失败时返回带 pipeline 链接的明确错误。集成节点（`mergeWorkBranchIntoIntegrate`）识别该错误为「已排队、等流水线」事件而不失败，也不直推；合并后由现有 MR 交付状态轮询（`refreshExternalDelivery`/`refreshGitLabDelivery`）推进——复用已有等待机制，不新增节点状态。GitHub 在 required checks 下仍是原有行为（重试预算用尽后失败），未改动。
  - 不删分支：创建 MR 带 `remove_source_branch=false`、合并带 `should_remove_source_branch=false`，即使项目开了 `remove_source_branch_after_merge=true`，promote（集成分支→默认分支）合并后也不会删掉集成分支，工作分支同样保留，和 GitHub 一致。
  - 凭据与库内存储沿用上游：令牌存在 `git_http_credentials`（与 GitHub 令牌同机制、脱敏、API/日志不回显），无新增列或迁移。GitLab Issue 拉取不在本次范围。

  - 派发按需求类型而非来源：缺陷修复 SOP 的派发由 `Kind`（`"issue"` → 缺陷修复泳道）驱动，不按 `Source` 分支，因此 GitLab Issue（`Kind="issue"`，与 GitHub 一致）与 GitHub Issue 派发路径完全相同，没有任何按来源分支的派发代码。
  - 不回写 GitLab：除 MR 交付状态刷新外，平台本就没有任何 Issue 状态回写，这里也不新增。
  - 界面：定时任务的来源选项「只同步 GitLab」仅当项目绑定了 GitLab 仓库时出现；来源徽标/标签「GitLab」用自己的色调；需求抽屉的绑定说明显示「GitLab Issue」；来源文案为「GitLab #<iid>」；外部链接用 Issue 的 `web_url`（`/-/issues/N`）。
  - 测试（httptest 伪 GitLab）：翻页到最后一页、opened/closed 映射、store 分配不冲突编号、已编辑描述保留与未改动刷新、缺凭据报错，以及 `PullScheduleJob` 的来源门控（空/github 跳过、gitlab 拉取）。sqlite + PostgreSQL 17 绿。

### 已知限制

- GitHub 上 0 提交的 PR：GitHub 的 PR create 对「两分支间无提交」返回 422（No commits between），平台当前按 `auto_merge_failed` 计为失败（本次只给 GitLab 补了「无提交则不开 MR」的前置校验，GitHub 未改）。

### 行为变化

- A failed script node or command gate keeps its command, exit code and the tail of its output (80 lines, 4000 bytes) in the node output and error, and hands them to the node it reworks or retries. Before, the reworked node only saw `Run: exit status 1`. ### Kiro

- Kiro CLI reaches the platform session MCP server in a Docker conversation sandbox (D3, the real cause). The earlier `--trust-tools` change (below) was not enough: in the acceptance environment, whose `kiro-cli` login is an enterprise IAM Identity Center profile, workspace chat still reported `agentflow__*`, `workbench_tool_schema` and `submit_assistant_reply` unavailable and made no gateway request. Reproduced in a container against both `kiro-cli` 3.4.0 and 3.5.0: under this enterprise profile (`mcpSandboxing`/`sandboxNetworkMode` locked) `kiro-cli` only connects an HTTP MCP server on a **loopback** address — it counts a non-loopback server (`session.load.timing mcpServers:1`) but never dials it (`mcp.log` has only `[MCPConfigManager] Identity provider setting changed`). A Docker conversation's session relay is advertised at the platform container's non-loopback IP (`conversationDockerAccess`), so Kiro silently dropped it; platform-mode chat and requirement clarification worked only because their gateway is same-container loopback, and SOP nodes because their servers are loopback (the agent browser) or stdio (the gate server). Trust was never the differentiator — both `--trust-all-tools` and `--trust-tools=@builtin,@agentflow_session` connect on loopback and both fail on a non-loopback URL. The fix: for a Docker sandbox, the Kiro session gateway is now exposed as a **stdio** command MCP server (a `python3` bridge that pipes JSON-RPC to the relay URL) instead of an HTTP url. A stdio child is not subject to Kiro's MCP network sandboxing, so it reaches the relay, the same way the SOP gate server already does; `python3` is already required for the native approval hook. It applies in platform, workspace and resume conversations (all go through the one conversation-process start path), only for Kiro and only for a Docker sandbox, and touches neither the loopback agent browser, the `#28` clarification `permissions.yaml`, nor the D1 approval hook. Verified in a container end-to-end: `kiro-cli` 3.4.0, fed the exact `mcp.json` the fix emits, connects over stdio to a cross-container relay and the model calls a platform tool. Upgrading the pinned `kiro-cli` to 3.5.0 does **not** fix D3 and is not done.
- Kiro CLI trusts `@builtin` plus the session MCP in a workspace conversation. A conversation left in workspace mode launched `kiro-cli` with bare `--trust-all-tools`; headless Kiro only connects an MCP server it can name in `--trust-tools`, so it now runs `--trust-tools=@builtin,@<each MCP server>`: `@builtin` trusts every built-in tool (so `web_fetch`, `web_search` and any tool a future Kiro adds keep working, with no list to maintain), and naming each MCP server matches the form platform-mode chat and requirement clarification already use. This does not widen Kiro's write trust: platform writes proposed from a workspace phase still wait as drafts for a person (gateway catalog and draft flow), and SOP nodes keep `--trust-all-tools`. (This is the workspace trusting every built-in tool and naming the session MCP; it is necessary for built-in tools in workspace mode but, as the entry above records, was not what made the session MCP reachable — the D3 fix is #36, the entry above.)
- Requirement clarification (「帮我问清楚」) runs on the CLI picked in the clarification panel, Kiro CLI included. It still runs on the platform server in the checked-out repository: Kiro CLI uses the server's `kiro-cli` login (in Compose the login copy from `LOOPFORGE_KIRO_DATA_DIR`) and trusts only its read-only file tools (`read`, `grep`, `glob`) and the platform MCP server that takes `submit_clarification`; answer rounds resume the same Kiro session. File reads of both Kiro CLI and CodeBuddy clarifications are confined to the checkout (the requirement text can come from anyone who files an issue, and the rest of the server holds its secrets): Kiro CLI through a `fs_read` deny rule outside the checkout in its private `permissions.yaml`, CodeBuddy through a PreToolUse hook that refuses file-tool paths resolving outside it. Before, both could read any file the platform process could, e.g. `/proc/1/environ`. With no model chosen, a responsible user without a CodeBuddy key gets `kiro:auto` when the server can run it. The CodeBuddy-only refusal is gone: a missing `kiro-cli` or login, or a missing personal key of the chosen CLI, is refused before any checkout with what to configure. CodeBuddy clarifications are unchanged.

### 调度

- A new schedule job no longer runs on the next scheduler tick (D30). A Cron job first runs at the first Cron time after it is created, an interval job one interval after. Re-enabling a job, or changing its `cron` or `intervalSec`, restarts the count from that moment instead of running the occurrences missed meanwhile; the moment is kept in the server-managed `scheduleFrom` (stored in the job payload, no migration). Jobs saved before the upgrade that never ran count from service startup, so the upgrade does not fire them all at once. 「立即运行」 still runs at once.
- SOP trigger jobs with 「同步哪些来源」 set to GitHub, 工蜂 or TAPD pull that source into the project before dispatching, so one Cron both pulls and dispatches; 「所有已配置来源」 still only dispatches issues already imported. A trigger job that prefers the issue's SOP ignores the project default filled in on save (`workflowDefaulted`). Only running SOPs hold a project or machine slot: runs waiting on a human gate, failed or cancelled give it back, and approving, resuming or retrying them queues when the bucket is full. Idle containers of runs waiting on a human gate are reclaimed after 10 minutes instead of 2 hours (#27). **Existing data is not migrated**: issues imported earlier keep their duplicate numbers, and they have no `workflowDefaulted`, so a trigger job that prefers the issue's SOP still runs the default bound to them.

SOPs already adopted into a project are copies and keep their old graph. The product SOP delivers documents only and is unchanged.
- A conversation reply that is still running keeps running through a slow heartbeat. A poll, the conversation list, a follow-up message or a steer used to record it as interrupted after 45 seconds without a stored heartbeat; the process then cancelled the CLI and the next message failed with 「工作区正在使用或保存，请稍后重试」 for up to 15 minutes. Reads of a turn this process executes no longer reap it, and an unchanged heartbeat on MySQL no longer counts as a lost turn. On MySQL a heartbeat's age is measured on the database clock that stamped it, so skew between an API host and MySQL neither reaps a live turn nor keeps a dead one; whether a lease holder stopped renewing is likewise judged from `run_workspace_checkpoints.lease_renewed_at`, stamped on the database clock, not from another replica's `lease_until`. When a turn whose process died is reaped, the workspace lease it recorded is released if nothing renewed it for 45 seconds, so the next message starts at once; a lease another turn took, one still renewed on another replica, and a background save are kept. `migrations/032_assistant_generation_workspace_lease.sql` adds the three columns by hand; startup AutoMigrate adds them too.

- The platform image bundles DeepSeek Harness `@deepseek-ai/dsh@0.2.2-rc.1` next to Codex and CodeBuddy, so a DeepSeek key works in conversations and SOP roles without an install step. 0.3.8 had no `dsh` and answered a DeepSeek Harness chat with “AI 助手生成失败，请稍后重试”. The image download grows by about 180 MB. An installation without the image installs the same pinned version from the conversation: every dsh release is a prerelease requiring Node 24.9, and npm on Node 22 found no version for the bare package name.
- A conversation workspace whose image lacks the chosen CLI installs Cursor CLI and Antigravity again. The sandbox drops every capability, so the installer's `tar` running as root could not restore the archive owner (`Cannot change ownership to uid 2000`), and the turn failed with “准备 cursor 原生CLI失败”. The workspace install of DeepSeek Harness uses the pinned `@deepseek-ai/dsh@0.2.2-rc.1` with relaxed engines, as the platform install already did; the bare package name resolved to no version.
- A conversation workspace on a custom Dockerfile without Node.js, npm or Python 3 runs the CLIs bundled in the platform image (Codex, CodeBuddy, DeepSeek Harness). The platform copies its Node.js, npm and a relocatable Python 3.12 into `${LOOPFORGE_DATA_DIR}/cli/toolchain/<build>/` on first use, and a bundled CLI the first time a sandbox needs it; every sandbox mounts that directory read-only at the end of `PATH`, so tools shipped by the image still win. The platform image gains python-build-standalone (about 30 MB to download, checked against a pinned SHA-256). Other CLIs are still installed inside the sandbox, now with the mounted npm. A musl (Alpine) or foreign-architecture image, which lacks the loader the copied `node` needs, keeps its own `PATH` and installs with its package manager as before. Each platform build gets its own directory of about 200 MB plus the CLIs it copied; directories of earlier builds are not removed, so delete the other `cli/toolchain/<build>/` directories after an upgrade.
- A DeepSeek Harness reply longer than 8 KB (about 2,700 Chinese characters) is shown in full. `dsh --json` cuts every event string at 8 KiB and only its `final` event carries the whole answer, so the chat stopped mid-sentence while the saved reply was complete.
- SOP sandboxes of the published image install OpenCode, Kimi Code and Pi on first use, as they already did for Claude Code. An SOP role on one of these CLIs used to fail with `exec: <cli>: not found` (exit 127) even after a conversation installed it.
- Run logs and telemetry redact every environment variable ending in `_API_KEY`, `_TOKEN`, `_SECRET` or `_PASSWORD`. Agent CLI keys such as `DEEPSEEK_API_KEY`, and `AGENTFLOW_CLI_API_KEY` used with a custom Base URL, used to appear in clear text in the `docker exec` line of an SOP run log, readable by project members. Rotate a key that ran an SOP role before this release.
- Upgrading with `./start.sh pull` now re-applies the schema pieces gorm AutoMigrate cannot create: the `run_telemetry.adapter` and `run_logs.level` generated columns from `migrations/001_run_obs_generated_columns.sql`, and the `INSERT IGNORE` starter catalog. A data volume from an older release no longer fails with `Error 1054 Unknown column 'adapter'` the first time someone opens a run detail. The installer and the upgrade command share one script, `scripts/install-schema-extensions.sh`, and a failed step stops the command with the migration file an operator has to run by hand.
- Deleting a conversation removes its shared native root (`shared/<hash>`). It used to stay on disk, about 73 MB each because every root holds its own CLI home with the CodeBuddy plugin marketplace, so a scheduled task that replaces its previous run on every cycle grew the disk by one root per run. The daily session janitor also removes roots left behind earlier once their conversation is gone and they have not changed for a day.
- CodeBuddy no longer downloads its built-in plugin marketplaces into every conversation and workspace. Each one has its own CLI home, so each new conversation used to take about 72 MB; it now takes under 1 MB. LoopForge installs no CodeBuddy plugins, and conversations that already downloaded the marketplaces keep working.
- Native conversation roots move to `AGENTFLOW_CONVERSATION_DIR`, which `compose.yaml` sets to `${LOOPFORGE_DATA_DIR}/conversations`. They used to sit in the `platform-data` volume under `/data/assistant`, a path the host Docker daemon does not have, so opening a conversation workspace on a Compose installation failed with `mkdirat ... read-only file system`. Attachments and other per-user assistant data stay in `/data/assistant`; nothing needs moving. A customised `compose.yaml` needs the same setting. `docs/deployment.md` now spells out the upgrade steps: update the checkout, then `./start.sh pull`.
- The built-in `generic-backend` Dockerfile includes `openssh-client` again, matching the platform image, so a `generic-docker` workspace or SOP sandbox starts on the platform image instead of building `agentflow-img-*` on first use. #207 added the package to the platform image but not to the starter catalog. The installer and `./start.sh pull` run `migrations/031_generic_backend_openssh.sql`, which updates the row only while it still holds the unedited previous default.
- `docs/deployment.md` splits `migrations/` into scripts the installer already covers, scripts an upgrade must run once, and scripts that only backfill existing rows.
- The 预览/源码 switch in the chat artifact preview now matches the 30px copy and download buttons beside it (36px on narrow screens) instead of using the 48px page-level tab size.
- Requirement clarification, Bot replies, run evals and the SOP preview build list only CodeBuddy models, because they run on CodeBuddy. `POST /api/chat-clarify`, `POST /api/issues/{id}/chat-clarify` and `POST /api/runs/{id}/eval` answer 400 for a model of another CLI (such as `codex:…`) instead of switching it to the CodeBuddy default; a Codex model saved earlier in these pickers falls back to the CLI default (#228).

- Repository clone URLs no longer carry credentials. Saving a `cloneUrl` with a user name or password, such as `https://user:token@github.com/acme/app.git`, is rejected with a pointer to the Git token in personal settings; the repositories API, bootstrap payload, run, task and requirement views, and the runner task management list strip credentials from `cloneUrl` and `webUrl` of rows saved earlier; a `webUrl` with credentials is rejected on save; runner clone errors and redacted Git output mask them. `ssh://git@host/...` and `git@host:path` remotes are still accepted.

Repositories saved earlier with a token in `cloneUrl` keep cloning until they are saved again. Saving one from the studio stores the URL without the token, so first put the Git token in 个人配置, then save the repository. Until then the token also lands in each workspace's `.git/config`, where the agent can read it, so re-save such repositories soon after upgrading.

Startup AutoMigrate creates the tables and columns of migrations `028` to `035`, and the installer and `./start.sh pull` apply `031`. `030` only aligns the stored `shared` flag of `generic-docker` with what the application already reads and is optional. To add the 「发起 MR」 node to the built-in SOPs of an existing installation, run `migrations/033_generic_sop_mr_node.sql` by hand (see `docs/deployment.md`). Rotate any agent CLI key that ran an SOP role before this release.

## 0.3.8 — header sign-in hardening and a GHCR mirror option

- With `AGENTFLOW_TRUST_IDENTITY_HEADERS=true`, identity headers such as `Staffname` are ignored on requests that carry `X-Forwarded-For`, `Forwarded` or `X-Real-IP`, unless the gateway also sends `X-AgentFlow-Gateway-Secret` matching the new `AGENTFLOW_IDENTITY_HEADER_SECRET`. A client behind a pass-through reverse proxy could otherwise sign in as any account. Deployments with the option off are unaffected.
- MCP, REST and quick-access snippets copied from an HTTPS studio use `https://` endpoints, so agents no longer send their Bearer token over cleartext HTTP.
- `MIRROR=<host> ./start.sh` pulls `<host>/tencent/loopforge:<version>` and tags it back to the name pinned in `compose.yaml`. `ghcr.nju.edu.cn` is one such host. Unset `MIRROR` still pulls `ghcr.io` directly. `MIRROR=<host> ./start.sh pull` refreshes through the same host. Setting `MIRROR` trusts that host. The published image stays on GHCR, and the GitHub Release records its digest. `registry-mirrors` such as `https://docker.nju.edu.cn` only accelerates Docker Hub.
- The release workflow publishes GHCR only. It no longer copies the image to `ccr.ccs.tencentyun.com`.
- The assistant asks before handing a requirement to an SOP, does not run a rejected proposal, and no longer runs the same draft twice after a timeout.
- The side browser renders sandbox dev servers natively instead of through screencast frames.
- The workbench shows the image's short git commit in the corner.
- The AI orchestrator's canvas build animations are back, and follow the dark theme.
- The chatbot clears the missing-key notice once quick access saves a key.
- Sandbox Git cleanup keeps `index.lock` while a process holds it through a bind-mounted or hard-linked path.
- Tool messages and executor output are clipped on UTF-8 character boundaries.

Before upgrading a deployment that signs users in by header behind a proxy adding forwarding headers, set `AGENTFLOW_IDENTITY_HEADER_SECRET` and have the gateway send it in `X-AgentFlow-Gateway-Secret`; otherwise header sign-in falls back to guest after the upgrade. See `docs/deployment.md`.

No migrations are required.
